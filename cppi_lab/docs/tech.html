§1.1Floor & Safety Buffer State Kernel

↔ Theory §1.1 · CPPI Invariant Wealth Floor & Safety Buffer Derivation

The trigger is a pure function of the two state variables. It lives in engine/kernel_numba.py and is compiled once and inlined into the main loop:

@njit(cache=True, nogil=True)
def trigger_price(n, c, floor_value, base_floor, keep):
    if n > QTY_EPS:                      # 1e-8 BTC
        need = floor_value - c
        if need < 0.0:
            need = 0.0
        required = need / (n * keep)      # (F - c) / (n (1 - gamma))
        if required > base_floor:
            return required
    return base_floor                     # P_liq / (1 - gamma)

The loop-invariant scalars are computed once per run: gamma = f_taker + delta_slip, keep = 1.0 - gamma, floor_value = n0 * p_liq + c0 and base_floor = p_liq / keep.

Execution priority inside a bar

Step 1 of every bar calls trigger_price on the state left by the previous bar. Step 2 tests the bar's low against it before anything else is allowed to touch the position:

p_floor = trigger_price(n, c, floor_value, base_floor, keep)        # step 1
if n > QTY_EPS and l_t <= p_floor:                                   # step 2
    p_trig = p_floor
    if o_t < p_floor:              # the bar opened through the trigger: a gap
        p_trig = o_t
        ...record the gap bar...
    c = c + n * p_trig * keep      # c_t = c_{t-1} + n_{t-1} P_trig (1 - gamma)
    n = 0.0
    ...cancel the resting order, reset the miss counter, event = 7...

The comparison is <=: a low that merely touches the trigger fires it. The cash update is the single expression of TSD §3.1; the reported execution price is p_trig * (1 - delta_slip) and the reported cost is n * p_trig * gamma.

Precision

All accounting is IEEE-754 float64. When the second term of the maximum binds, the exit proceeds are $n \cdot \frac{F-c}{n(1-\gamma)} \cdot (1-\gamma)$, which equals $F - c$ only up to rounding: a few units in the last place, about $10^{-11}$ USD for a 60,000 USD floor and about $10^{-7}$ at the top of the allowed ranges. This is why the conservation assertion is $V_t \ge F - 10^{-6}$ (FLOOR_TOLERANCE_USD) and not a strict inequality. The kernel is compiled without fastmath (§5.1), so the comparison l_t <= p_floor means the same thing on every platform.

§1.2Cushion & Recoverable BTC Accounting

↔ Theory §1.2 · Whipsaw Decay as Dynamic Put Replication Cost

Recoverable inventory and cushion

f_eff = (1.0 - rho) * f_maker + rho * f_taker        # once per run
n_max = n + c / (c_t * (1.0 + f_eff))                # every bar, at the close
v_t    = c + n * c_t * keep
margin = v_t - floor_value
row.cushion_usd = margin if margin > 0.0 else 0.0    # C_t = max(0, V_t - F)

n_max is recomputed from scratch every bar from the two state variables; nothing is accumulated, so there is no drift to correct.

Cost bookkeeping

Every execution adds its explicit cost to the bar's fee_paid_usd and to one of two run totals:

ExecutionCash changeCost recorded
Maker sell of $q$ at $P_{\text{lim}}$$+q P_{\text{lim}}(1 - f_{\text{maker}})$$q P_{\text{lim}} f_{\text{maker}}$
Maker buy of $q$ at $P_{\text{lim}}$$-q P_{\text{lim}}(1 + f_{\text{maker}})$$q P_{\text{lim}} f_{\text{maker}}$
Taker sell of $q$ at the close $C_t$$+q C_t (1 - \gamma)$$q C_t \gamma$
Taker buy of $q$ at the close $C_t$$-q C_t (1 + \gamma)$$q C_t \gamma$
Emergency exit of $n$ at $P_{\text{trig}}$$+n P_{\text{trig}}(1 - \gamma)$$n P_{\text{trig}} \gamma$

Taker friction is additive, matching the emergency formula: fee and slippage are both charged on the notional at the reference price. The run totals STAT_MAKER_FEES_USD and STAT_TAKER_COSTS_USD feed the Fees + Slippage card, and the sum of the fee_paid_usd column equals their sum exactly; the test-suite asserts it. Cumulative whipsaw bleed is therefore available three ways: as dollars of explicit cost, as the fall of n_max below $N_0$, and as the fall of cushion_usd.

The rebuy cap

The cap of Theory §1.2 and §2.1 is rebuy_cap(). Its feasibility test evaluates the envelope on the state a purchase of $q$ would create:

def _post_buy_slack(q, n, c, price, unit_cost, ...):
    c_post = c - q * unit_cost
    if c_post < 0.0:
        return -1.0                                  # cannot be paid for
    n_post = n + q
    floor_post = trigger_price(n_post, c_post, floor_value, base_floor, keep)
    span = max(p_ref - floor_post, 1.0)
    d_post = clip01((price - floor_post) / span)
    n_max_post = n_post + c_post / (price * (1.0 + f_eff))
    return sell_ceiling(n_max_post, d_post, k_sell, s_down) - n_post   # >= 0 is feasible

unit_cost is the dearer of the two routes, price * (1 + max(gamma, f_maker)), so the cap covers the taker child and the maker child of a split order together. rebuy_cap(target, minimum, ...) then proceeds in three steps:

  1. the target, limited to what cash can pay, is tried first and returned if feasible (one evaluation, the normal case);
  2. otherwise the minimum quantum $\Delta n_{\min}$ is tried, and zero is returned if even that is infeasible (two evaluations, the cash-locked case, which would otherwise be re-solved on every bar);
  3. otherwise a 40-step bisection (CAP_ITERATIONS) between the feasible minimum and the infeasible target converges on the edge. The lower end is returned, so the result is always feasible whatever the shape of the slack function.

A capped quantity below $\Delta n_{\min}$ is discarded rather than traded.

§2.2Order Routing Engine (route_order_by_rho)

↔ Theory §2.2 · Continuous Risk-Aversion (ρ) & Urgency Escalation Theory 
@njit(cache=True, nogil=True)
def execution_urgency(is_sell, d, s_down, s_up, m_miss):
    if is_sell:
        return 1.0 - d * (1.0 - s_down) * 0.5**m_miss
    return s_up * (1.0 - 0.5 ** (m_miss + 1))

@njit(cache=True, nogil=True)
def taker_fraction(rho, urgency):
    if rho <= 0.0:
        return 0.0                 # rho = 0: never a taker child
    if rho >= 1.0:
        return 1.0                 # rho = 1: always all taker
    if urgency >= 1.0 - rho:
        return 1.0                 # escalation
    return rho                     # split

@njit(cache=True, nogil=True)
def route_order_by_rho(is_sell, dn, d, s_down, s_up, m_miss, rho, maker_dominated):
    theta = taker_fraction(rho, execution_urgency(is_sell, d, s_down, s_up, m_miss))
    if maker_dominated:            # f_maker >= f_taker + delta_slip
        theta = 1.0
    q_taker = theta * dn
    return q_taker, dn - q_taker

The branch order matters at the boundary: with $\rho = 0$ and $u_t = 1$ the escalation test $u_t \ge 1 - \rho$ would be true, and it is the earlier rho <= 0.0 branch that makes $\theta = 0$ hold identically, as TSD §2.4 requires. The maker child is computed as dn - q_taker rather than (1 - theta) * dn so the two children add up to the order exactly in floating point.

Children

  • A taker child above QTY_EPS executes immediately at the close: a sell nets q * c_t * keep, a buy costs q * c_t * (1 + gamma). The reported price is $C_t(1 \mp \delta_{\text{slip}})$.
  • A maker child above QTY_EPS becomes the single resting order (pend_side, pend_qty, pend_px = c_t). It lives for exactly one bar: step 3 of the next bar fills or misses it, and step 4 of that bar posts a fresh one at the new close if the envelope still asks for a trade.

The miss counter

m_miss counts consecutive misses of the current rebalance, tracked by chain_side:

EventEffect
Maker order misses (step 3)m_miss += 1
Maker order fills (step 3)m_miss = 0
Step 4 places no order (the holding is back inside the band)m_miss = 0, chain_side = 0
Step 4 places an order on the other sidem_miss = 0, chain_side = side
Emergency exitm_miss = 0, chain_side = 0

A full taker escalation leaves the counter alone: if the very next bar still needs to sell, it starts from the urgency already reached instead of posting a hopeful maker order again.

Verification

tests/test_routing.py checks the three regimes on real windows: at $\rho = 0$ the only taker executions are code-7 liquidations; at $\rho = 1$ there are no maker fills and no misses; for interior values every split order has a taker child of exactly $\rho\,\Delta n$ and every escalated order has none left to post.

§3.1Stochastic Fill Sampler & PCG64 Seeding

↔ Theory §3.1 · Stochastic Order-Book Liquidity & Pass-Through Theory

Fill probability

@njit(cache=True, nogil=True)
def fill_probability(is_sell, limit_px, qty, open_, high, low, close,
                     opposing_vol, atr, lambda_liq, beta_vel, alpha_size):
    if is_sell:
        penetration = high - limit_px
        adverse = open_ - close
    else:
        penetration = limit_px - low
        adverse = close - open_
    if penetration <= 0.0:
        return 0.0
    if adverse < 0.0:
        adverse = 0.0
    phi_pen = 1.0 - math.exp(-lambda_liq * (penetration / atr))
    phi_vel = math.exp(-beta_vel * (adverse / atr))
    absorb = max(0.01 * opposing_vol, 1e-8)
    phi_size = 1.0 / (1.0 + (qty / absorb) ** alpha_size)
    return clip01(phi_pen * phi_vel * phi_size)

atr is signals.atr[t]: the decline-signal ATR already floored at 1 USD by the signal pipeline. opposing_vol is buy_vol[t] for a resting sell and sell_vol[t] for a resting buy.

Resolution

if p_fill > 0.0 and u[t] <= p_fill:
    ...fill at pend_px, fee f_maker, m_miss = 0, event 1 or 3...
else:
    ...event 5 or 6, m_miss += 1...

The explicit p_fill > 0.0 guard matters because Generator.random() draws from $[0, 1)$: without it a variate of exactly 0.0 would fill an order the bar never reached. Every attempt writes p_fill_prob; bars without an attempt carry NaN there, which is what pane 3 and the ledger use to tell "no order" from "zero probability". u_rand_draw holds $U_t$ on every bar.

Seeding

def uniform_draws(seed, n_bars):
    return np.random.Generator(np.random.PCG64(int(seed))).random(n_bars)

One vector of $T$ variates per run, indexed by bar. PCG64 and NumPy's double conversion are specified bit for bit, so a seed gives the same vector on Linux, Windows and macOS; tests/test_prng.py pins the first values of seed 42. The controller caches the vector on (seed, T), so dragging a strategy slider never redraws it.

Monte Carlo ensemble

engine/monte_carlo.py runs the same compiled simulate_core once per member inside a parallel loop:

@njit(cache=True, nogil=True, parallel=True)
def ensemble_core(..., u_block, ..., equity, stride, stats):
    for m in prange(u_block.shape[0]):
        simulate_core(..., u_block[m], ..., False, equity[m], stride, stats[m])
  • Counter seeding. Member $m$ uses PCG64(s_rng + m); member 0 is the trajectory on screen, which tests/test_monte_carlo.py verifies bar for bar.
  • Draws. draw_block() fills the $M \times T$ block in a thread pool (NumPy releases the GIL while filling). For 30 days that is 4.32 million variates, 34.6 MB. Blocks up to 96 MB are cached by the controller; longer windows are processed in batches of at most 96 MB.
  • Telemetry is off. With write_rows = False the loop writes only $V_t$, sampled every stride bars with stride = ceil(T / 43200), so the equity matrix never exceeds about 35 MB.
  • Percentiles. percentile_band() sorts each sample column in a second parallel loop and interpolates linearly between order statistics, matching np.percentile.
  • Threads. The OpenMP threading layer is requested first (engine/__init__.py). The user interface runs the ensemble on a worker thread and never starts a second one while the first is running; a request that arrives in the meantime marks the result stale and is served when the worker returns.

§4.1Vectorized Signal Pipeline

↔ Theory §4.1 · Asymmetric Decline & Growth Microstructure Signals

Both signals depend only on the market window and ten parameters, so they are computed as whole arrays before the state machine starts (engine/signals.py) and reused until one of those inputs changes. Each building block is one linear pass.

FunctionComputesCost

Implementation notes

  • Rolling sums are recomputed, not updated. The usual add-the-new, subtract-the-old update accumulates rounding error over half a million bars. The window is at most 60 bars, so each sum is formed afresh, newest sample first. The result has no drift and agrees with the reference implementation to the last bit.
  • Rolling extrema use a monotonic deque held in a preallocated index array: each bar is pushed and popped at most once, so a 1,440-bar breakout window costs the same as a 30-bar one.
  • Start of the window. An EMA is seeded with its first sample, $\mathcal{E}_W(X)_0 = X_0$. Rolling sums and extrema use the bars available so far while the window is still filling. Signals never look at bars before $t = 0$, so a back-test depends only on the window it is given.
  • Constants. The normalisers 1.5 and 2.0, the 0.40 imbalance saturation and the 1 USD floors are module constants named after their role (MOMENTUM_DOWN_ATR_MULT, IMBALANCE_SATURATION, ATR_FLOOR_USD, …).

Synthesised taker volume

Sources without a taker split (Coinbase candles, plain OHLCV files) get one from the close location value in data/loader.py:

def clv_split(high, low, close, volume):
    frac = np.clip((high - close) / np.maximum(high - low, 1e-8), 0.0, 1.0)
    sell = volume * frac
    return volume - sell, sell          # (buy, sell)

The resulting dataset is flagged synthesized_flow=True and the dataset selector says so, because the imbalance of such a file is a function of candle shape, not of recorded aggression.

Caching

SimulationController keys the signal arrays on the market-window key plus the tuple of SIGNAL_PARAM_KEYS. Changing a fee, $\rho$, a liquidity parameter or the seed reuses them; only the kernel reruns.

§5.1Numba State-Machine Loop & Telemetry Schema

↔ Theory §5.1 · Discrete-Time Execution Model, Event Ordering & Gap Risk

simulate_core() in engine/kernel_numba.py is one loop over the bars. Its body is the five steps of TSD §3.1 plus one sub-step.

StepActionEvents
1p_floor = trigger_price(n, c, …) on the previous end state.
2If n > QTY_EPS and low <= p_floor: emergency taker sale of everything at min(open, p_floor); cancel the resting order.7
3If not liquidated and an order rests: compute p_fill, compare with u[t], fill at the limit or record the miss.1, 3, 5, 6
3bAfter a maker buy fill only: recompute the trigger on the new state; if low <= post_floor, emergency sale at min(limit, post_floor).7
4Envelope at the close; route any order; execute the taker child; post the maker child.2, 4
5Compute $V_t$, update the conservation statistics, write the telemetry row.

The TSD calls this a 24-column buffer; the dtype it lists has 26 fields, and the dtype is what is implemented.

More than one event in a bar

The schema has one event_code per bar, but a bar can hold two events: a maker order resolved in step 3 and a taker child executed in step 4, which is the normal shape of an escalation. The row records the highest-priority one,

7 liquidation > 2, 4 taker fill > 1, 3 maker fill > 5, 6 miss

and nothing is lost: a parallel uint8 array flags carries one bit per event code (1 << (code - 1)) for everything that happened in the bar. The chart markers, the ledger filters and the ledger's event label (TAKER_SELL +MISS_SELL) are all driven by the flags, and the counts on the KPI cards come from a statistics vector accumulated inside the loop, not from scanning the event column.

Conservation assertion

margin = v_t - floor_value
if not gapped:
    if margin < stats[STAT_MIN_MARGIN_USD]:
        stats[STAT_MIN_MARGIN_USD] = margin
    if margin < -FLOOR_TOLERANCE_USD:          # 1e-6
        stats[STAT_FLOOR_BREACHES] += 1.0

gapped becomes true on the first bar whose open is below its trigger at a step-2 liquidation; that bar's index is STAT_GAP_BAR. A non-zero breach count on a run that never gapped would be a defect; the property tests drive the kernel through thousands of windows, seeds and parameter sets and require it to be zero.

Floating-point guards

  • No fastmath. The kernels are decorated @njit(cache=True, nogil=True). fastmath would let the compiler assume there are no NaNs, which the telemetry uses as a sentinel, and reorder arithmetic, which would make results differ between CPUs. Without it the kernel takes about 1.6 ms for 43,200 bars against a 15 ms budget, so nothing is lost.
  • Bit-exact reference. tests/reference.py is a plain-Python interpreter of the same state machine, one method per step. The test-suite requires all 26 fields and the flags to be equal, not close, across randomised windows, seeds and parameters.
  • Clamps. A maker sell fills min(pend_qty, n); a maker buy fills at most what cash can pay; a taker sell is limited to n. Each is a no-op in exact arithmetic and protects against the last bit of rounding driving a balance negative.
  • Thresholds. QTY_EPS = 1e-8 BTC decides "flat"; FLOOR_TOLERANCE_USD = 1e-6 decides "below the floor".

Chart renderer

ui/chart_workspace.py builds one pyqtgraph.GraphicsLayoutWidget with three plots at stretch 55 : 25 : 20 whose x axes are linked. pyqtgraph provides the layout, the view ranges and the mouse interaction; it paints nothing. The workspace assembles two display lists for ui/chart_gl.py: the scene (grid, layers, markers, liquidation flashes, axes and tick labels) and the overlay (crosshair, liquidation badges, read-outs). Both are drawn in a single pass on the OpenGL viewport. Moving the crosshair rebuilds only the overlay and replays the scene from buffers that are already on the GPU.

Every layer keeps its full-resolution series together with a pyramid of block minima, maxima and sums (ui/chart_geometry.py). For the range in view it is reduced to at most two points per pixel - a min/max reduction for prices and holdings, a bucket mean for the fast oscillating signals and envelope edges - and tessellated into triangles in screen space, which a small shader anti-aliases and cuts into dashes. Text and markers are rasterised once into a sprite atlas and drawn as textured quads. Line weight and dashing therefore do not depend on the driver's line-width support, and the cost of a frame depends on the canvas width, not on the length of the back-test. Without an OpenGL viewport the same display lists are drawn with QPainter.

Ledger

TelemetryTableModel (ui/ledger_window.py) is a QAbstractTableModel over the structured array. A view row is an entry of one int64 index vector; filtering rebuilds it from the flags, sorting applies a stable argsort of the chosen column to it. Selecting a row emits barActivated, which moves the chart's selection line; clicking the chart emits barSelected, which selects and reveals the row. Export writes the rows currently shown, in display order, as CSV or Parquet.

Docking

The ledger and this documentation viewer are CDockWidget instances of the Qt Advanced Docking System. The first time one is opened it floats, and its container gets the flags Tool | WindowStaysOnTopHint | WindowMinimizeButtonHint | WindowMaximizeButtonHint, so it stays above the main window. Where an X11 window manager does not show utility windows, the container is an ordinary window owned by the main window instead of a Tool window. Dragging its title bar over the main window shows the drop compass, and dropping on the left, right or bottom indicator docks it there; the menu next to each toolbar button performs the same docking without a drag. On Linux the drag needs the X11 platform, which the application selects when it is usable (see the README); there the floating windows have the application's own title bar and resize grips along their edges.

Popovers

RichPopoverManager (ui/popover_manager.py) owns three precise single-shot timers: 150 ms from entering a ? badge to showing the card, 300 ms of grace after leaving the badge or the card, and a short fade. Entering the card cancels the grace timer; Pin detaches the card into a movable one and a fresh transient card serves the next hover. The body is a page served from cppidoc://popover/<id> and rendered with the bundled KaTeX; clicking one of its links is intercepted in acceptNavigationRequest and forwarded to MainWindow.open_documentation(volume, anchor).

Counterpart preview

DocWorkbench (ui/doc_workbench.py) places two QWebEngineView instances in a splitter at 65 : 35. The script assets/doc_sync.js runs in both. In the primary view it finds the <section data-concept-id> at the reading line with an IntersectionObserver and calls bridge.notifySectionFocused(id) over a QWebChannel; hovering a cppidoc:// link calls bridge.notifyLinkHovered(volume, anchor). DocSyncBridge relays both to the workbench, which runs cppiDoc.focusSection(id) in the preview to scroll it to the counterpart and mark it with the left border. When the preview is collapsed the script asks bridge.sectionSnippet() for the title and summary and shows them in a floating card instead.
